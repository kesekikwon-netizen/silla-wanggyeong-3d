### Implication for Strata 3D (Q1)
- **ADD a glTF 2.0 (.glb) exporter/importer for the heritage models. Keep the custom binary mesh only as an internal cache.** glTF 2.0 is the one ratified, vendor-neutral payload that 3D Tiles, Cesium, Esri, Blender and game engines all read. Use KHR_mesh_quantization or EXT_meshopt_compression plus KHR_texture_basisu for size. Put provenance/licence (KHS source, evidence tier, survey date) in **KHR_xmp_json_ld** so the data stays attached when a model is exchanged.
- **ADD 3D Tiles 1.1 as the streaming/exchange container for terrain-draped site collections** (311 sites, implicit tiling, 3D Tiles 1.1 structured metadata per feature). It is the ratified OGC CS and it maps onto cesium-native, which is C++ and Apache-2.0 and could be evaluated for a Qt/OpenGL integration. **Do not target 3D Tiles 2.0 or glTF 2.1 yet.** Both are proposals; design so External Assets can be adopted later.
- **Gaussian splats: ADD as an optional read path only.** The base KHR_gaussian_splatting is ratified per the Khronos registry, but the SPZ compression extension, which is what Cesium actually streams, is not ratified and has a moving name (`_spz` vs `_spz_2`). If heritage scans arrive as splats, store them as base-extension glTF with the COLOR_0 fallback, so viewers without splat support still show a point cloud.
- **I3S: do not adopt.** Esri-centric, OGC version unchanged since 1.3 (2023). Read it only if an Esri partner delivers SLPK.
- **CityGML 3.0 / CityJSON: optional export for building-scale reconstructions with semantics.** It does not fit terrain or streaming. CityJSON is simpler than GML if added.
- **Recommended 2026 choice:** heritage models → **glTF 2.0 (GLB)**; collections and terrain streaming → **3D Tiles 1.1** (quantized-mesh or glTF terrain tiles); archival survey rasters → COG.

### Implication for Strata 3D (Q2)
- **KEEP OSGeo4W GDAL (now 3.13.3, current).** Note the 3.13 shared-library major-version bump: rebuild and relink rather than mixing DLLs. OSGeo4W lags upstream by one release for PROJ (9.8.1 vs 9.9.0) and PDAL (2.10.0 vs 2.10.2). That is fine. Pin versions in CMake and log `GDALVersionInfo`/`proj_info()` at startup.
- **MIGRATE viewshed/terrain analysis to GDAL's algorithms** (`GDALViewshedGenerate` or the `gdal raster viewshed` CLI with `--mode cumulative`, angle/pitch masks, curvature coefficient) instead of in-house code. Cumulative viewshed suits "intervisibility between hillforts/tombs" presentations.
- **ADD COG + GTI for DEM/orthophoto mosaics.** Convert NGII/Copernicus tiles to COG, index them with GTI (GeoPackage index), and read only the window around Gyeongju. Use `gdal driver cog validate` in tests.
- **ADD PDAL (OSGeo4W) for point clouds: COPC 1.0 as the on-disk/streamable format, LAZ 1.4 as the interchange format.** `filters.m3c2` (2.10) supports excavation/erosion change detection between survey epochs. PDAL reads/writes SPZ, a possible bridge to splat data.
- **PROJ:** EPSG:5186/5187 are standard EPSG codes. Make sure `proj.db` ships with the app and that the OSGeo4W PROJ_DATA path resolves at runtime. Run a transformation regression test whenever PROJ is upgraded, given the EPSG revert in 9.8.1.

### Implication for Strata 3D (Q3)
- **MIGRATE the DEM from Copernicus GLO-30 to NGII DEM where available.** It is free, has no use restriction and comes as .img (presumably Erdas Imagine, which GDAL reads; confirm on a real file). Convert it to a COG in EPSG:5186/5187. **Keep GLO-30 as the fallback** with the DLR/Airbus attribution (Copernicus DEM release 2024_1, July 2024, opened: https://dataspace.copernicus.eu/explore-data/data-collections/copernicus-contributing-missions/collections-description/COP-DEM). Check the actual NGII grid size (5 m?) on a downloaded tile with `gdalinfo` before advertising a resolution.
- **ADD an NGII 수치지도 V2.0 (NGI) importer through GDAL/OGR** if the 2D sibling app does not already supply these layers as SHP. Show the 공공누리 Type 1 attribution in the map credits. Building outlines with UFID (Type 1, verified) could replace OSM Overpass buildings in Korea. 건물높이공간정보 was seen only as a menu item; its licence was not checked.
- **ADD NGII 정사영상 (map.ngii.go.kr) and VWorld Satellite WMTS as the satellite imagery sources** (see Q4). VWorld needs a per-user API key in settings. Read the VWorld 이용약관 for caching rules before enabling a disk tile cache. That has not been verified (see the unverified list).
- **ADD a KHS 3D data import path.** Downloaded heritage scans and assets (e.g., 천년 신라 왕경, 첨성대) could replace or validate the schematic Blender models. Before any redistribution or bundling, record per-asset licence terms; they were not found on the portal. Use the 2025 data.go.kr CSV catalogue (Type 1) for search and linking by heritage ID.

### Implication for Strata 3D (Q4)
- **MIGRATE away from the current "Google XYZ satellite tiles" immediately.** If the app fetches `mt*.google.com`-style XYZ URLs without a Map Tiles API key/session, it has no licence at all. Even through the official Map Tiles API, the app's offline/disk caching, prefetching around Gyeongju, and use beside non-Google layers (VWorld, OSM, NGII) conflict with §3.2.3(a)(b)(e) and the Map Tiles policy ("offline use … prohibited").
- **Photorealistic 3D Tiles: do not add for this app.** The renderer itself would be allowed (third-party renderers are allowed), but offline field use, disk caching and display next to non-Google layers conflict with the verified rules. *(Inference, not stated in the policy: exported PNG/PDF sheets that include 3D tiles imagery may also be problematic. Check with Google before relying on it.)* Mixing with KHS/NGII overlays raises the "non-Google map" question (§3.2.3(e)). Korean coverage is unverified.
- **Replacement stack:** (1) **VWorld Satellite WMTS** for online imagery, keyed, with attribution; (2) **NGII 정사영상** downloaded once and converted to COG for offline presentations, licence to be confirmed per product; (3) Copernicus DEM / NGII DEM for terrain. Keep a provider abstraction so a provider can be switched off per its terms.
